Problem Framing / 项目解决什么问题

这个项目解决的不是“让语音助手能聊天”，而是一个更工程化的 agent reliability 问题： 当用户说出一条浏览器操作命令时，系统能否把它变成一条受约束、可验证、可回放的浏览器任务， 并且在模糊、危险、网页漂移或视觉证据不足时诚实停止。

面试中的一句话版本：我做了一个中文优先的有界 Voice-to-Browser Agent，把 spoken command 转成结构化任务，再通过 validator、confirmation gate、route policy、视觉 grounding 和 trace evidence 证明“为什么能执行、为什么要停、执行到了哪里”。

用户问题

语音命令天然有 ASR 噪声、指代不完整、口语化、省略和中英混说，不能直接交给浏览器执行器。

工程问题

多数 demo 只展示最终 UI，缺少结构化中间态，reviewer 难以判断一次 agent 行为是否可靠。

安全问题

登录、付款、下载、提交、私有数据输入等动作必须停在 confirmation 或 blocked 状态，而不是“模型觉得可以”。

证据问题

真实运行会产生 raw audio、截图、cookies、浏览器 profile、provider 响应等敏感信息，公开材料必须只用 sanitized artifact。

Bounded Scope / 项目边界

项目定位是 standalone bounded Chinese-first Voice-to-Browser Agent demo。它接受一次上传、录制、 fixture 或手动 transcript 输入，输出一条结构化浏览器任务、澄清请求、确认请求或阻断结果。

Architecture / 项目架构

1. Input 语音上传、录制、fixture transcript 或 typed command。
2. ASR primary/fallback/fixture adapter 生成 transcript，并保留 provenance。
3. Normalize rule、mock LLM 或 configured provider 产出结构化候选。
4. Validate schema、intent type、slot、安全 flags、confirmation 由确定性逻辑决定。
5. Route 路由到 demo preview、live controlled、public-readonly、clarification 或 blocked。
6. Execute 本地浏览器执行；视觉任务调用 browser-use-vision dependency boundary。
7. Evidence 写入 Execution Trace、visual verification result、sanitizer status 和 release pack。

Execution Flow / 一次命令如何执行

  1. 用户在 Operator Console 输入 transcript，或上传/录制一条音频。
  2. 系统产生 ASR transcript；真实音频路径支持 operator review 和 edit。
  3. Normalizer 产出 BrowserTaskRequest 或 ClarificationRequest，并记录 normalizer provenance。
  4. Validator 检查 intent type、required fields、public task slots、safety flags 和 confirmation 状态。
  5. Route selector 根据任务类型、配置和安全策略选择 demo_preview、live_controlled 或 live_public_readonly 等 evidence mode。
  6. Confirmation Gate 在 payment、checkout、login、private data、mutation 等场景前暂停或阻断。
  7. Browser executor 运行本地受控页面或 opt-in read-only public task；视觉任务记录 grounding refs。
  8. Agentic controlled flow 把 action success 和 visual verification result 分开，失败或 uncertain 时 re-observe、recover 或 stop。
  9. Trace Writer 输出 sanitized execution trace，release pack 只采纳 privacy_scan passed 的证据。

项目开发阶段以及每个阶段的原因

阶段 0：项目边界
做了什么：通过 CONTEXT.md 和 ADR 明确 voice layer 与 browser-use-vision 分离；本项目只拥有 spoken-command execution。
为什么：避免把已有视觉 grounding 项目改成语音插件，也避免把项目讲成大而泛的语音助手。
阶段 1：MVP schema 与 preview evidence
做了什么：定义 BrowserTaskRequest、ClarificationRequest、 ExecutionTrace、demo fixture、normalizer、validator 和 dry-run preview traces。
为什么：先证明“语音命令到结构化任务”的中间表示和安全边界，再谈真实浏览器执行。
阶段 2：live controlled 与 agentic vision
做了什么：增加 live_controlled、agentic observe-act-verify traces、 icon/color/SVG/dashboard 等视觉重任务。
为什么：preview 不足以说明系统真的能操作页面；但真实公网不稳定，所以先用可复现本地 controlled pages 验证视觉闭环。
阶段 3：Operator Console v2/v3
做了什么：从 fixture dropdown 走向 command-first console，加入 audio transcript review、 route cards、normalizer provenance、visible result 和 raw trace inspection。
为什么：面试官和 reviewer 需要看到系统如何做决定，而不是只看到一个自动化脚本输出。
阶段 4：public-readonly lane
做了什么：增加 allowlisted docs/reference/GitHub read-only task contracts、 completion verifier、reliability matrix、visible artifact policy。
为什么：让项目能触达真实公开页面，但必须通过 task contract、No login、No mutation、private-by-default artifact 保持边界。
阶段 5：LLM structured normalizer
做了什么：加入 rule、mock LLM、configured provider normalizer path 和 safe provenance； LLM 输出只能作为候选，必须过 schema、validator、confirmation 和 route policy。
为什么：真实口语理解通常需要 LLM，但执行权不能交给 LLM；确定性 gate 才是安全边界。
阶段 6：dataset / eval / release pack
做了什么：从 sanitized trace 生成 Speech-to-Task seed set、deterministic splits、 held-out adaptation evaluation、normalizer comparison 和 reviewer release pack。
为什么：把项目从“能跑”提升到“能复核、能比较、能作为 future adaptation input”，但不声称训练完成。
阶段 7：final completion audit
做了什么：统一 README、public evidence page、closeout checklist、interview overview、 OpenSpec main specs 和 tests。
为什么：最终交付的风险不是缺功能，而是 claim drift；所有对外材料必须和证据边界一致。

Safety and Privacy Gates / 安全与隐私门

Normalizer Validator

拒绝缺字段、unsupported intent、长链路目标、任意 URL、危险 public task slots。

Confirmation Gate

checkout、payment、posting、login、private data、file transfer、irreversible submit 会 pause、cancel 或 block。

Public-Readonly Policy

只允许 read-only navigation/search/extract；No login、No mutation、No account workflow、No arbitrary URL。

Sanitizer

公开 artifact 排除 raw audio、raw screenshots、cookies、credentials、local paths、remote host details、raw provider data。

评测指标及含义

本项目的评测目标不是给模型做排名，而是衡量 Speech-to-Task 输出、执行证据、安全边界和 artifact 是否足够可靠。下面这些指标来自 scripts/build_speech_to_task_eval.py、 scripts/build_demo_evidence_pack.py、release pack manifest 和测试文档。

结构化 Speech-to-Task 指标

指标 含义 为什么重要
schema-valid rate 候选输出能否解析为 BrowserTaskRequest 或 ClarificationRequest。 Agent 执行前必须有强 schema；自然语言相似不等于可执行。
output-kind accuracy 候选输出是 browser task 还是 clarification，是否和 target kind 一致。 把应澄清的问题误执行，是比“文本不够像”更严重的错误。
intent-type accuracy 候选 intent_type 是否匹配目标任务类型。 search、click visual target、fill form、select filter、extract/compare 的执行策略完全不同。
required-slot match rate public task 所需 slot，如 site hint、query、owner/repo、package name 是否保留。 只读公网任务依赖 task contract；slot 丢失会导致错误路由或误报完成。
safety or clarification decision accuracy 候选是否同样落入 route-ready、confirmation-required、blocked 或 clarification。 安全决策比 wording 更关键；该停的必须停。
route-ready rate 候选输出通过 deterministic validator 且不需要 confirmation 的比例。 它不是越高越好；安全敏感任务被 confirmation 拦住时，route-ready 会下降但行为正确。
fallback rate LLM/provider 路径失败后走 rule fallback 或 clarification fallback 的比例。 体现 provider 不稳定时系统是否仍能安全降级。
failure slices 按 candidate mode、split、evidence mode、target kind、intent type、schema status、安全类别分组的失败切片。 帮助定位错在 schema、intent、slot、安全策略还是某类证据模式。

执行与证据指标

指标/字段 含义 如何解读
final_status succeeded, stopped, blocked, failed, pending_confirmation, clarification_required 等。 不是所有非 succeeded 都是坏结果；安全停止和澄清本身是设计目标。
execution_mode / evidence_mode 区分 preview、controlled live、agentic controlled、real voice、public-readonly。 避免把 controlled showcase 误说成真实公网执行。
visual verification result passed, failed, uncertain，附 expected condition、observed state、reason、proof refs。 action clicked 不等于视觉状态达成；视觉 verification 是第二层证据。
public_completion_state completed, partial, stopped, failed, blocked。 公网只读任务只有满足 task-specific proof 才能 complete；打开页面不等于成功。
privacy_scan / sanitizer_status artifact 是否通过隐私扫描，以及是否 public-safe、pending 或 failed。 公开材料可信度取决于 artifact 边界，而不是 raw runtime 输出多少。

Adaptation Dataset Output / Speech-to-Task 数据输出

Dataset workflow 把 sanitized Execution Traces 转为本地 adaptation seed examples，并支持 --evaluation-splits 生成稳定 train/dev/test split。它的目标是 future Speech-to-Task adaptation 输入，而不是 ASR/TTS 数据集或模型训练结果。

uv run python scripts/build_speech_to_task_eval.py \
  --dataset-manifest runtime/speech-to-task-adaptation-dataset/manifest.json

关键产物：runtime/speech-to-task-adaptation-dataset/manifest.json, runtime/speech-to-task-adaptation-dataset/examples.jsonl, runtime/speech-to-task-adaptation-eval/manifest.json, runtime/speech-to-task-adaptation-eval/summary.json。

Adaptation Evaluation Output / 评测输出

Evaluation harness 在 held-out split 上比较 rule、deterministic mock LLM 或未来 candidate JSONL 输出。 每条 candidate 都必须 example-id matched；缺失、重复、extra id 或 malformed output 会被显式记录为失败。

报告包含 split counts、candidate modes、schema-valid rate、output-kind accuracy、intent-type accuracy、 required-slot match rate、safety or clarification decision accuracy、route-ready rate、fallback rate、 row counts、failure slices、source manifest path 和 privacy-scan status。

这只是 local adaptation-readiness evidence。它不是 model fine-tuning，不发布 checkpoint，不评估 ASR/TTS 质量， 不证明 production readiness，也不证明 broad public-web automation。未来 fine-tuning 应作为 separate future project。

Guardrail wording: not fine-tuning, not checkpoint publication, not ASR/TTS evaluation, not public leaderboard ranking, not production readiness, and not broad public-web autonomy.

Limitations / 诚实边界

这个 closeout MVP 不包含 model fine-tuning、expanded dataset collection、public hosting、 broad public-web automation、checkpoint 发布、ASR/TTS 质量评测、账号工作流、验证码绕过或写操作。 如果后续要做模型适配训练，应作为 separate future project，复用当前 seed/eval artifacts。

visual verification loop evidence 默认是 keyless deterministic verifier over controlled local pages。 real VLM/provider verification is optional and local/private；不会把 raw screenshots、raw annotated images、 provider-private payloads 或 remote host details 放进 release evidence。

Interview Talk Track / 面试讲法

  1. 先讲问题：语音命令到浏览器执行不是 NLP rewrite，而是受约束 task construction。
  2. 再讲架构：ASR adapter、reviewed transcript、structured normalizer、validator、route、executor、trace。
  3. 强调边界：LLM 只生成候选；确定性 validator 和 confirmation gate 决定是否能执行。
  4. 展示证据：打开 docs/public-evidence/index.html 或 release pack manifest，按 evidence mode 讲。
  5. 讲评测：schema-valid、intent、slot、安全决策、route-ready、visual verification、privacy_scan。
  6. 最后讲取舍：为什么 fine-tuning、公网写操作、账号自动化和 public hosting 都被放到 scope 外。

面试官可能问到的问题以及回答

Q1：这个项目最核心的贡献是什么？

核心贡献是把 spoken command 到 browser execution 做成一个有边界、可审计的系统。 不是只接 ASR 和浏览器自动化，而是定义了 Browser Task Request、Clarification Request、 validator、confirmation gate、route decision、visual verification result 和 sanitized trace。 面试时我会强调：项目的价值在“可靠执行和证据链”，不是泛化语音助手。

Q2：为什么不直接把 ASR 文本丢给 browser agent？

因为 ASR 文本可能不完整、含糊或危险，比如“打开那个页面”“帮我提交”“搜索 GitHub 好项目”。 直接执行会把歧义和风险转移给浏览器 agent。我的做法是先把文本转成强 schema，然后用 deterministic validator 判断是否可执行；不明确就 clarification，敏感就 confirmation，越界就 blocked。

Q3：LLM 在系统里承担什么角色？会不会绕过安全逻辑？

LLM 只承担 structured-output normalizer 的候选生成角色。它可以输出 Browser Task Request 或 Clarification Request，但必须通过 schema parsing、Normalizer Validator、Confirmation Gate 和 route policy。即使 LLM 输出了看似合理的任务，只要 intent、slot、安全状态或 public contract 不满足，就不会进入执行。

Q4：为什么项目要复用 browser-use-vision，而不是自己写视觉模型？

项目目标是 Voice-to-Browser application reliability，不是重新做视觉 grounding 引擎。 browser-use-vision 已经负责 OCR、region、SoM/visual context 等视觉能力，本项目通过 dependency boundary 调用它，自己负责 voice-to-task、safety、route、execution trace 和 reviewer evidence。 这样边界清晰，也避免复制已有项目代码。

Q5：如何证明这不是一个只会 dry-run 的 demo？

证据模式分层：demo_preview 证明 normalization 和 safety； live_controlled 证明本地受控页面真实执行； agentic_live_controlled 证明 observe-act-verify； real_vision_controlled 调用真实 visual grounding dependency； real_voice_controlled 覆盖真实音频 review 路径。 每层都有独立 trace 路径和 release-pack manifest。

Q6：为什么 public-readonly 做得这么保守？

因为真实网页有登录态、验证码、速率限制、UI 漂移、账号动作和隐私风险。 所以 public-readonly 被设计成 opt-in、allowlisted、task-contract based、No login、No mutation， 并且 completion verifier 必须看到 task-specific proof 才能 completed。否则就记录 partial、stopped、 failed 或 blocked，这比“硬说成功”更可靠。

Q7：visual verification loop evidence 解决什么问题？

浏览器 action 返回 succeeded 不代表目标视觉状态真的达成。比如 click 发生了，但按钮没变、目标 stale、 页面跳转到登录或目标模糊。visual verification result 记录 expected condition、observed state summary、 proof refs、reason 和 recovery/stop decision，把“动作成功”和“任务完成”拆开判断。

Q8：评测指标为什么不用文本相似度？

因为这个任务的输出是可执行结构，不是摘要文本。两个句子相似不代表 intent、slot、安全决策正确。 所以评测看 schema-valid rate、output-kind accuracy、intent-type accuracy、required-slot match rate、 safety or clarification decision accuracy、route-ready rate、fallback rate 和 failure slices。

Q9：route-ready rate 不是 1.0，是不是效果不好？

不一定。当前本地 eval 里 route-ready rate 为 0.75，是因为 held-out 样本中包含 confirmation-required 场景。安全敏感任务不应该 route-ready；它应该停在 confirmation gate。因此这个指标要结合 safety decision accuracy 一起看。

Q10：项目如何防止隐私泄漏？

公开材料只使用 sanitized artifacts。Sanitizer 和 tests 会阻止 raw audio、raw screenshots、browser profile、 cookies、credentials、private URL、local file URI、raw provider prompt/response、remote host detail 等进入公开证据。 public-readonly 的截图和 raw trace 默认留在本地 runtime/，只有通过 sanitizer 才能作为摘要证据。

Q11：如果 ASR 识别错了怎么办？

Operator Console 支持 transcript review：真实音频先生成 ASR transcript，operator 可以查看 adapter metadata、 confidence/diagnostics 并编辑 reviewed transcript，再进入 normalizer。trace 会保留原始 ASR、reviewed text、 edit status 和 provenance，避免把 ASR 错误伪装成模型成功。

Q12：这个项目为什么没有训练模型？

当前目标是完成应用层可靠性闭环和 evidence pack。项目已经能导出 Speech-to-Task seed set、splits 和 held-out evaluation harness，但 dataset 规模和任务定位还不适合在同一 closeout 中加入训练和 checkpoint 发布。 更合理的路线是把训练作为 separate future project，复用现有 examples 和 eval harness。

Q13：如果网页 UI 漂移或公网被限制，系统如何处理？

对 controlled pages，系统通过 deterministic visual verification 和 recovery/stop 决策处理 stale 或 uncertain。 对 public-readonly，GitHub captcha、verification、login boundary、rate limit、network error、selector drift 都会被映射为 blocked、stopped、failed 或 partial，而不是继续尝试绕过。

Q14：你会如何现场 demo？

我会先跑 command-first console：输入一个清晰 controlled visual command，再展示 route card、normalized request、 visual proof 和 trace JSON。然后演示一个 ambiguous command 产生 Clarification Request，一个 checkout command 进入 Confirmation Gate。最后打开 release pack 或 docs/public-evidence/index.html，说明证据模式和指标。

Q15：如果让你继续做下一阶段，你会做什么？

我会把下一阶段拆成两个方向：一是扩大 reviewed Speech-to-Task 数据并做真正的 adaptation/fine-tuning； 二是增加更多稳定 public-readonly contracts 和真实 VLM verification 的 local/private 对照。 但我仍会保持 task contract、安全门和 sanitizer 作为基础边界。

Q16：这个项目和你其它 agent reliability 项目如何呼应？

它补的是 application depth：从评测/证据系统走到一个可交互的 end-to-end agent 应用。 共同点是都强调 bounded scope、inspectable artifacts、failure taxonomy、fresh validation 和 reviewer-friendly handoff。
